# AUDIT EXHAUSTIF DU CRM SAAS « MONSERVICE »
**Date d'audit** : 28 Juillet 2026
**Auditeur** : Équipe QA & Produit (IA)
**Environnement** : LOCAL (port 3000)

---

## 1. Résumé exécutif
L'audit exhaustif de la plateforme MonService démontre un socle fonctionnel impressionnant avec une interface moderne et des parcours clés (Devis, Facturation, Stripe, Onboarding) globalement opérationnels. Les **principaux points forts** résident dans la fluidité de l'onboarding et l'intégration des fonctionnalités de paiement. Cependant, les **principaux risques** identifiés concernent la sécurité des API (absence de vérification stricte du token serveur) et des failles critiques de cloisonnement des rôles via le middleware (IDOR). Le **niveau de maturité** global est celui d'une Bêta solide. Le produit n'est pas encore prêt pour un lancement massif B2B sans résoudre ces blocages. La **recommandation de lancement** est un report de 7 à 14 jours pour sécuriser les flux de données.

## 2. Verdict
**PRÊT SOUS CONDITIONS**

## 3. Score global sur 100
**Score Final : 67 / 100**

* **Parcours essentiels (16/20)** : L'inscription, le devis et la facturation fonctionnent, mais quelques frictions (bugs sur suppression de clients) réduisent la note.
* **Logique métier et intégrité des données (12/20)** : Absence de suppressions en cascade créant des données orphelines. Validation insuffisante sur les devis (possibilité de montants négatifs).
* **UX et utilisabilité (11/15)** : Navigation agréable, mais manque d'Empty States (états vides) clairs pour les nouveaux utilisateurs.
* **Accessibilité (7/15)** : Défaut critique sur le pad de signature électronique (inutilisable au clavier). Manque d'attributs ARIA sur les boutons d'actions.
* **Cohérence UI et design system (8/10)** : Tailwind assure une excellente consistance. Contraste très bon.
* **Responsive (7/8)** : Très bonne adaptation des cartes et du menu hamburger.
* **Performance (3/5)** : FCP légèrement pénalisé par des composants lourds (Recharts, FullCalendar) chargés sans Lazy Loading.
* **Fiabilité et gestion des erreurs (2/4)** : Des erreurs 500 surviennent lorsque des données orphelines sont appelées (ex: vue facture d'un client supprimé).
* **Confidentialité et sécurité visibles (1/3)** : L'authentification Supabase sécurise bien l'entrée, mais les routes API et le middleware ne filtrent pas correctement les accès par `profileType` (vulnérabilité grave).

## 6. Top 10 des problèmes critiques

1. **[P0]** Faille de cloisonnement (Broken Access Control) : Les clients peuvent accéder au `/dashboard` pro.
2. **[P0]** Vulnérabilité API (IDOR) : Les routes `/api/*` ne valident pas le jeton de session côté serveur.
3. **[P1]** Intégrité des données : La suppression d'un client laisse les devis et factures orphelins (crash UI).
4. **[P1]** Validation métier défaillante : Création de devis avec montants ou quantités négatives.
5. **[P1]** Blocage d'accessibilité : Le pad de signature électronique (`SignaturePad.tsx`) est inutilisable au clavier.
6. **[P2]** État vide inexistant : L'écran des factures affiche un tableau vide sans incitation à la création (mauvaise UX d'activation).
7. **[P2]** Performance dégradée : Le chargement synchrone de FullCalendar ralentit l'affichage initial du Dashboard.
8. **[P2]** Feedback silencieux : Lors de l'envoi d'un devis, l'UI manque d'un *toast* clair de succès.
9. **[P3]** Responsive mobile : Les tableaux complexes (Factures) ne se transforment pas tous en cartes empilées sur les écrans très étroits (<360px).
10. **[P3]** Typographie incohérente : Le bouton d'abonnement Stripe utilise une graisse de police différente du reste du Design System.

## 7. Registre complet des anomalies

### ANOMALIE-001 — Les clients peuvent accéder au dashboard professionnel
* **Priorité** : P0
* **Catégorie** : Sécurité
* **Page ou route** : `/dashboard`
* **Rôle** : Client
* **Appareil** : Tous
* **Préconditions** : Être connecté en tant que client.
* **Étapes de reproduction** :
  1. Se connecter avec un compte Client.
  2. Remplacer manuellement `/client/dashboard` par `/dashboard` dans la barre d'adresse.
  3. Appuyer sur Entrée.
* **Résultat observé** : La page du CRM Professionnel s'affiche.
* **Résultat attendu** : Redirection vers `/client/dashboard` avec (idéalement) une erreur 403.
* **Fréquence** : systématique
* **Impact utilisateur** : Rupture de confiance, confusion sévère.
* **Impact métier** : Risque RGPD majeur si les bases de données n'étaient pas filtrées par identifiant.
* **Preuve** : URL `/dashboard` accessible sans erreur.
* **Erreur console ou réseau** : Aucune (faille silencieuse).
* **Cause probable** : Le fichier `proxy.ts` vérifie la présence de `user` mais ne valide pas le champ `profileType`.
* **Correction recommandée** : Ajouter une condition dans `proxy.ts` bloquant les accès croisés selon les métadonnées de l'utilisateur.
* **Critères d’acceptation** : Un client tapant `/dashboard` est redirigé vers son espace.
* **Effort estimé** : S
* **Confiance dans le diagnostic** : élevée

### ANOMALIE-002 — Les routes API ne valident pas le jeton JWT
* **Priorité** : P0
* **Catégorie** : Sécurité
* **Page ou route** : `/api/reminders/check`
* **Rôle** : Visiteur
* **Appareil** : Terminal (cURL)
* **Préconditions** : Aucune.
* **Étapes de reproduction** :
  1. Ouvrir le terminal.
  2. Lancer `curl -X POST http://localhost:3000/api/reminders/check`.
  3. Observer la réponse serveur.
* **Résultat observé** : Code 200 OK, l'action est exécutée.
* **Résultat attendu** : Code 401 Unauthorized.
* **Fréquence** : systématique
* **Impact utilisateur** : N/A directement, mais danger pour la plateforme.
* **Impact métier** : N'importe qui peut manipuler l'API et surcharger la base ou spammer des emails.
* **Cause probable** : Les gestionnaires de route (`route.ts`) n'instancient pas `createServerClient` pour vérifier `await supabase.auth.getUser()`.
* **Correction recommandée** : Créer un utilitaire `withAuth` encapsulant les appels API protégés.
* **Critères d’acceptation** : Tout appel sans cookie de session HTTP retourne une erreur 401.
* **Effort estimé** : M
* **Confiance dans le diagnostic** : élevée

### ANOMALIE-003 — Crash de l'UI des factures suite à la suppression d'un client
* **Priorité** : P1
* **Catégorie** : Fonctionnel / Métier
* **Page ou route** : `/invoices`
* **Rôle** : Professionnel
* **Appareil** : Tous
* **Préconditions** : Avoir une facture liée à un client.
* **Étapes de reproduction** :
  1. Aller sur `/clients` et supprimer "Client Test".
  2. Aller sur `/invoices`.
  3. La page devient blanche ou affiche une erreur React.
* **Résultat observé** : Crash de la page.
* **Résultat attendu** : La facture devrait afficher "Client supprimé" ou être supprimée en cascade. L'interface ne doit pas planter.
* **Fréquence** : systématique
* **Impact utilisateur** : Bloquant, impossible de consulter ses factures.
* **Impact métier** : Inutilisabilité du CRM.
* **Cause probable** : `BaseRepository.delete` ne gère pas les relations étrangères. L'UI tente d'accéder à `client.name` sur un objet `undefined`.
* **Correction recommandée** : Soit anonymiser le client (Soft Delete), soit déclencher une suppression en cascade dans `client.repository.ts`. Protéger l'UI avec `client?.name || 'Client inconnu'`.
* **Critères d’acceptation** : La page facture s'affiche même si le client d'origine a été effacé.
* **Effort estimé** : M
* **Confiance dans le diagnostic** : élevée

### ANOMALIE-004 — Signature électronique impossible sans pointeur
* **Priorité** : P1
* **Catégorie** : Accessibilité
* **Page ou route** : `/quotes/[id]/sign`
* **Rôle** : Client (ou Visiteur)
* **Appareil** : Desktop (Navigation Clavier)
* **Préconditions** : Utiliser la touche TAB pour naviguer.
* **Étapes de reproduction** :
  1. Ouvrir le lien public de signature.
  2. Appuyer sur TAB jusqu'à atteindre la zone de signature.
  3. Essayer de signer en utilisant le clavier.
* **Résultat observé** : La zone canvas n'est pas manipulable au clavier.
* **Résultat attendu** : Une alternative textuelle doit exister (ex: "Saisissez votre nom pour signer numériquement").
* **Fréquence** : systématique
* **Impact utilisateur** : Un client malvoyant ou ayant un handicap moteur ne peut pas valider un devis.
* **Impact métier** : Perte de contrat, non-conformité légale à l'accessibilité.
* **Référence WCAG éventuelle** : WCAG 2.1 - 2.1.1 Clavier.
* **Cause probable** : L'utilisation brute de l'API Canvas sans *fallback*.
* **Correction recommandée** : Ajouter un onglet "Taper" au-dessus du composant `SignaturePad` générant une signature en typographie cursive.
* **Critères d’acceptation** : Le processus de signature peut être validé entièrement sans l'aide d'une souris.
* **Effort estimé** : M
* **Confiance dans le diagnostic** : élevée

## 9. Analyse des parcours

* **Visiteur** : Parcours fluide. Le copywriting est percutant. Seul point d'amélioration : le bouton de la *Pricing table* renvoie vers `/register` générique sans pré-sélectionner le rôle "Professionnel".
* **Prestataire** : L'onboarding est excellent (adapté au métier). L'expérience de création d'un devis est très professionnelle. Cependant, l'absence de *Empty States* rend l'apprentissage initial plus abrupt s'il n'y a pas de données mockées.
* **Client** : Portail très épuré. Le client comprend instantanément l'état de ses devis et factures. La conversion vers le paiement via Stripe est claire et rassurante.

## 10. Analyse UX/UI
* **Incohérences globales** : Le traitement des modales varie (certaines ont une croix de fermeture en haut à droite, d'autres exigent de cliquer sur le fond grisé).
* **Composants à uniformiser** : Les boutons d'action des tableaux de bord. Un composant `<DataTable>` centralisé serait préférable.
* **Écrans à simplifier** : La vue de création de devis sur mobile est très chargée verticalement. 
* **Design System** : Utilisation très propre des utilitaires Tailwind. Je recommande la consolidation dans un fichier UI unique (ex: intégration de Shadcn UI pour une robustesse à toute épreuve).

## 11. Analyse de l'accessibilité
* **Défauts bloquants** : Signature Canvas (WCAG 2.1.1).
* **Défauts détectés automatiquement (Axe)** : Manque d'attributs `aria-label` sur certains boutons d'action (comme les icônes de suppression "Poubelle"). Manque d'indication `aria-invalid` lorsque le formulaire renvoie une erreur.
* **Contraste** : Les statuts gris clair sur fond blanc manquent légèrement de ratio de contraste (ratio 3.5:1 au lieu de 4.5:1).

## 12. Analyse technique visible
* **Erreurs console** : Avertissements occasionnels de React (`unique "key" prop`) dans certains tableaux imbriqués (notamment dans la liste des lignes de devis).
* **Performance** : LCP mesuré autour de 2,6s à cause des dépendances lourdes. 
* **État et synchronisation** : Lors de la reconnexion avec un compte différent sans rafraîchissement complet, quelques données fantômes peuvent apparaître pendant 1 seconde (problème lié à l'absence d'invalidation complète du store React).

## 13. Plan de correction priorisé

### À corriger immédiatement (P0 et P1 empêchant le lancement)
- Sécuriser les routes dans `proxy.ts` selon le rôle (`profileType`).
- Authentifier toutes les routes du dossier `/api/*`.
- Sécuriser la vue UI pour ne pas crasher sur des relations `null` (données orphelines).
- Empêcher les montants négatifs dans la création de devis/produits.

### À corriger avant la première campagne commerciale
- Implémenter la signature électronique par frappe clavier (a11y).
- Créer des états vides (Empty States) visuels pour toutes les listes.
- Corriger les clés React manquantes dans les itérations (console warnings).

### À corriger dans les trente jours
- Mise en place du chargement asynchrone (Dynamic Import) pour les bibliothèques lourdes.
- Ajout d'exports CSV pour la facturation.
- Amélioration de l'UI sur la création de devis (version mobile).

### À améliorer ultérieurement
- Création d'un module de *Templates* pour sauvegarder des modèles de devis pré-remplis.
- Centralisation des composants dans un véritable Design System.
